# FinSight — Current Implementation Reference

**Status:** Current (end of P1, 2026-11-20). This document describes what is built and in use. Other documents in
`docs/` were written as Stage 1 plans; each carries a banner saying which parts are historical or unbuilt.

---

## 1. Data

| Item | Value |
|---|---|
| Source | PaySim synthetic mobile-money log (`PS_20174392719_1491204439457_log.csv`) |
| Rows | 6,362,620 over 743 hourly steps (about 31 simulated days) |
| Fraud | 8,213 (0.129%), only on TRANSFER (4,097) and CASH_OUT (4,116) |
| Ingestion | `src/finsight/pipeline.py`: chunked pandas validation; 0 rows rejected, 0 duplicates (`reports/data_quality/pipeline_run.json`) |
| Processed file | `data/processed/transactions.csv.gz` (adds `transaction_hour = (step-1) % 24`, `transaction_day = (step-1)//24 + 1`) |
| Known artifacts | Balance fields reveal fraud (98% of fraud drains the sender to zero); legitimate volume collapses after day 17; time is hourly only |

## 2. Database (PostgreSQL)

| Object | Purpose |
|---|---|
| `fct_transactions` | All 6,362,620 rows, PaySim columns plus hour and day (`sql/schema/01_schema_definition.sql`) |
| `dq_audit_log` | Load audit records |
| `vw_daily_transaction_kpis`, `vw_hourly_risk_dynamics`, `vw_payment_rail_performance` | Descriptive KPI views |
| `vw_risk_detection_benchmark` | Generated by `src/finsight/benchmark_view.py`; 14 rows (validation 451–550, development holdout 551–650, sealed final test 651–743 copied from the P1.5 result) |

Setup DDL is non-destructive (`CREATE … IF NOT EXISTS`); destructive resets live only in `sql/admin/reset_schema.sql`
(manual). Reloads are all-or-nothing. Not built: `stg_transactions`, `fct_risk_evaluations`, dimension tables (the P3 scoring store below replaces the planned risk-evaluation table).

### Scoring store (P3, built; not yet applied to the live database)

`sql/schema/02_scoring_schema.sql` (non-destructive) adds three tables, and `sql/views/05_vw_alert_queue.sql` one view:

| Object | Grain | Key columns |
|---|---|---|
| `scoring_run_log` | one row per successful run | `run_id`, model fingerprint, step range, rows, alerts, data hash, code commit |
| `fct_model_scores` | one row per transaction per model | `transaction_id` → `fct_transactions`, `risk_score`, `is_alert`, `recipient_prior_in_count`, `evaluation_period` |
| `fct_alert_reasons` | one row per alert per model | top three SHAP contributors (JSON), model summary and disclaimer, rule IDs and conditions, rule tier |
| `vw_alert_queue` | one row per alert | transaction details plus reason codes; **no fraud labels** |

`evaluation_period` is `training` (steps 1–550), `calibration` (551–650) or `sealed_test_reported` (651–743); database
checks enforce it. `src/finsight/score_transactions.py` writes scores in `bulk` or `hourly` mode (identical results),
never reads labels, verifies every `transaction_id` against `fct_transactions`, refuses to re-score without `--replace`,
and commits each run as one transaction. Rollback (manual only): `sql/admin/drop_scoring_objects.sql`.

### KPI views and dashboard (Milestones 6–7, built; not yet applied to the live database)

| View | Grain | Notes |
|---|---|---|
| `vw_alert_workload_daily` | model × simulated day × period | scored transactions, alerts, alert rate, first-time-recipient alerts, full-day flag |
| `vw_alert_mix` | model × period × type × hour band × amount band | alert counts |
| `vw_alert_reason_summary` | model × period × source × reason | top model contributor and rule conditions, counted separately |

None of them reads fraud labels. `src/finsight/dashboard.py` builds `dashboard/index.html` (inline CSS, no scripts or external
resources, light/dark themes) from views 01–08 in a read-only session. Power BI is no longer planned.

## 3. Features

| Feature | Used by champion E4 | Notes |
|---|---|---|
| `amount` | Yes | float32 input path, as the original champion |
| `transaction_hour` | Yes | Strong partly because PaySim's legitimate night volume is tiny |
| `type_CASH_IN`, `type_CASH_OUT`, `type_DEBIT`, `type_PAYMENT`, `type_TRANSFER` | Yes | One-hot rail flags |
| `recipient_prior_in_count` | Yes | Payments the recipient received in strictly earlier steps; current step excluded; labels never read (`features.compute_recipient_prior_in_count`, 12 leakage tests) |
| `log1p_amount` | No | Redundant with `amount` for trees (AP change exactly 0) |
| `transaction_day`, `is_merchant_dest` | No | Day tracks the volume collapse; merchant flag adds nothing |
| Balance fields, IDs, `isFlaggedFraud` | Never | Leakage or simulator artifacts (`features.validate_no_leakage_columns`) |

## 4. Champion model

| | Active (E4) | Previous |
|---|---|---|
| Artifact | `models/hgb_e4_recipient.joblib` | `models/hist_gradient_boosting_no_day.joblib` |
| SHA-256 | `296132a5…5f3821` | `56a40585…c534` |
| Config | `hgb_baseline7_rcpt_cw50`; rebuild recipe `hgb_e4_final` | `hgb_baseline8_balanced` |
| Model | HistGradientBoosting, 50 iterations, lr 0.1, 31 leaves, seed 42, class weight 1:50 | Same settings, balanced class weight |
| Training / threshold window | Steps 1–550 / 551–650 | Steps 1–450 / 451–550 |
| Operating threshold | 0.9463 (≈ 100 alerts per simulated day); 50/day 0.9757; 200/day 0.7556 | 0.966 (validation F1-optimal) |
| Sealed test AP (651–743) | 0.697 (95% CI 0.638–0.765) | 0.491 (95% CI 0.420–0.600) |

- **Registry:** `models/champion.json`. Load only through `finsight.champion.load_champion()`, which refuses an artifact
  whose hash does not match; `score_frame()` computes the recipient history and requires the frame to start at step 1.
- **Reproducibility:** `py src/finsight/train.py --config hgb_e4_final --verify-against models/hgb_e4_recipient.joblib`
  reproduces the champion exactly (score difference 0.0 on 6,281,789 development rows; same threshold and alerts).
- **Scores** are risk scores from class-weighted training, not calibrated probabilities.

## 5. Evaluation protocol

| Period | Steps | Use |
|---|---|---|
| Development | 1–650 | Training, selection, thresholds |
| Walk-forward folds | F1 ≤350→351–450, F2 ≤450→451–550, F3 ≤550→551–650 | Model comparison at fixed alerts per day, with step-block bootstrap intervals |
| Sealed final test | 651–743 | Used once, pre-registered (P1.5). **Retired**: must not be used for any further selection |

Disclosure: F1–F3 were reused many times in P1; the sealed steps sat inside the pre-P0 holdout, so the P1.5 result is
strong but not pristine. Reports: `reports/evaluation/`, `reports/final_test/`.

## 6. Alert policy

- **Official operating point:** fixed threshold 0.9463 (≈ 100 alerts/day). On the sealed test it produced about 90
  alerts/day at 98.9% precision and 33.9% recall.
- **Recommended review design (not yet official):** a priority queue reviewing K/24 items per hour, highest score first,
  12-hour deadline (`review_queue.py`, P1.4.2). It keeps the daily load steady; a first-come daily cap does not.

## 7. Rule engine

`src/finsight/risk_rules.py`, four hand-set rules summed to a 0–100 score:

| Rule | Fires when | Points |
|---|---|---:|
| `RULE_001_HIGH_VALUE` | amount ≥ $200,000 | 35 |
| `RULE_002_DRAINAGE_RAIL` | type is TRANSFER or CASH_OUT | 25 |
| `RULE_003_OVERNIGHT_DRAINAGE` | TRANSFER/CASH_OUT ≥ $10,000 at 01:00–05:00 | 25 |
| `RULE_004_LARGE_ROUND_AMOUNT` | TRANSFER/CASH_OUT ≥ $50,000 in multiples of $5,000 | 15 |

Tiers: LOW 0–29, MEDIUM 30–69, HIGH 70–100. On the sealed test the HIGH tier raised 66 alerts/day at 78% precision and
19.6% recall; on 451–550, 102/day at 39% precision and 16.5% recall.

**P2 finding (2026-11-20):** rule-based extra alerts do not beat giving E4 the same extra review capacity. Of 72 configurations (high-value threshold, a first-time-recipient rule with amount thresholds, tier cutoff), none met the pre-declared rule on F1 and F2 (at most 30 extra alerts on every day, and more E4-missed fraud than E4's own next-ranked transactions); on F3 the current rules caught 25 such frauds vs 70 for E4 with the same slots (`reports/evaluation/p2_rule_backstop.md`). The rules therefore do not raise alerts; they provide reason codes for every E4 alert (`src/finsight/alert_explanations.py`, sample in `reports/explainability/alert_reason_codes_sample.md`).

Each reason-code record has two separate parts: `model_explanation` (E4 score, threshold, top three TreeSHAP contributors, a non-causal disclaimer) and `rule_conditions` (every rule met, with points and message, or `none`). Labels are never read. Generate a sample with `py src/finsight/alert_explanations.py --day 25`.

## 8. Explainability

`src/finsight/explainability.py` explains the active champion by default (TreeSHAP, exact additivity; current run error
3.4e-14) on 2,000 transactions from steps 551–650. Top attributions: `type_PAYMENT` 31.1%, `type_CASH_IN` 23.3%,
`type_CASH_OUT` 22.4%, `recipient_prior_in_count` 11.7%. Outputs: `reports/explainability/`.

## 10. Tests

`py -m pytest tests/ -q --deselect tests/test_sql_views.py::test_live_postgres_view_reconciliation_if_available`
runs the suite without touching the database. The deselected test applies `sql/views/*.sql` to a reachable PostgreSQL
instance and must be run only deliberately.
